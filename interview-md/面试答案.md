# 面试问题答案

## 项目总览

### Q：电商项目有哪些功能，怎么实现的？

A：我的项目是一个基于黑马点评业务改造的本地生活电商系统，后端用 Java 21、Spring Boot、MyBatis Plus、Redis、Redisson，前端用 Vue 3、Vite、Element Plus。核心功能包括登录、商铺浏览、商铺类型缓存、优惠卷秒杀、RAG 问答模块。

我重点做的是高并发秒杀和 Redis 缓存链路。秒杀入口不是直接打数据库，而是先执行 `seckill.lua`，在 Redis 里完成库存判断、一人一单判断、库存扣减和订单消息投递。订单消息写入 Redis Stream `stream.orders`，后台消费者异步落库。落库时再用 Redisson 用户维度锁和数据库唯一索引兜底，避免重复下单。

缓存方面，商铺详情通过 `CacheClient.queryWithLogicalExpire()` 做逻辑过期、互斥锁和异步重建；商铺分类用 Redis 普通缓存加互斥锁；附近商铺用 Redis GEO 查 10 公里范围内的店铺，再用 `order by field(id, ...)` 保持 Redis 返回顺序。

## Redis / 秒杀 / 并发

### Q：秒杀系统为什么要用 Redis 承接高并发入口？

A：秒杀请求量瞬间很高，如果所有请求都直接查数据库、扣数据库库存，数据库会成为瓶颈，还容易出现超卖和重复下单。所以我把资格判断前置到 Redis。Redis 是内存操作，Lua 脚本又能保证一段逻辑原子执行，很适合做秒杀入口的库存判断、一人一单判断和快速失败。

我的实现里，请求进入 `/voucher-order/seckill/{id}` 后，先在 Java 里校验秒杀券是否存在、是否开始、是否结束，然后生成订单 ID，执行 `seckill.lua`。Lua 成功后马上返回订单 ID，真正数据库落库由 Redis Stream 后台异步处理，这样前台请求链路很短。

### Q：Lua 脚本里具体校验哪些条件？

A：脚本主要校验两个条件：库存是否大于 0，以及当前用户是否已经下过这一张券。它用的 Redis key 是 `seckill:{voucherId}`，这是一个 Hash，里面有 `stock` 字段，也有 `user:{userId}` 字段。

流程是：先 `HMGET` 一次性取出库存和用户下单状态；如果库存不存在或小于等于 0，返回 1；如果用户已下单，返回 2；否则用 `HSETNX` 写入 `user:{userId}=1`，防止并发重复设置；然后 `HINCRBY stock -1` 扣 Redis 库存；最后 `XADD stream.orders` 投递订单消息。

### Q：库存怎么判断？

A：秒杀入口判断的是 Redis Hash 里的 `stock` 字段。服务启动时会把 `tb_seckill_voucher` 里的库存预热到 `seckill:{voucherId}` 的 `stock` 字段里。Lua 判断 `stock <= 0` 就直接返回库存不足；通过后用 `HINCRBY` 原子扣减 Redis 库存。

数据库层面，异步落库时还会执行一次 `stock > 0` 条件扣减：`setSql("stock=stock-1").gt(SeckillVoucher::getStock, 0)`。所以 Redis 是高并发入口判断，MySQL 是最终库存落库兜底。

### Q：一人一单怎么判断？

A：Redis 入口用 `seckill:{voucherId}` 这个 Hash 记录用户下单状态，字段名是 `user:{userId}`。Lua 里先读这个字段，如果是 1 就返回重复下单；如果没有，就用 `HSETNX` 设置。`HSETNX` 是原子操作，可以避免同一个用户并发请求时重复写入。

异步落库时还会再查一次 `tb_voucher_order`，按 `voucher_id + user_id` 判断是否已经有订单；数据库表上也有唯一索引 `uk_user_voucher(user_id, voucher_id)`，这是最后兜底。

### Q：除了 Redis 校验外，数据库里有没有兜底约束？

A：有。`tb_voucher_order` 表有唯一索引 `uk_user_voucher(user_id, voucher_id)`。即使 Redis 或业务代码出现边界问题，数据库也能拒绝同一个用户对同一张券重复插入订单。

异步消费者里如果遇到 `DuplicateKeyException`，会记录日志并按重复订单处理，不会让整个消费者挂掉。

### Q：唯一索引建在哪里？

A：建在订单表 `tb_voucher_order` 上，字段是 `user_id` 和 `voucher_id`，索引名是 `uk_user_voucher`。这个索引的语义就是“同一个用户对同一个优惠券只能有一条订单”。

关注关系表也有类似的唯一索引，`tb_follow` 上有 `uk_follow_user_pair(user_id, follow_user_id)`，保证同一对关注关系不重复。

### Q：校验通过后订单如何异步落库？

A：Lua 校验通过后，不直接落数据库，而是通过 `XADD stream.orders` 把 `userId`、`voucherId`、`id` 写入 Redis Stream。服务启动时会创建或确认 `stream.orders` 和消费者组 `g1`，然后启动后台线程消费。

消费者用 `XREADGROUP` 从 `stream.orders` 读取消息，转换成 `VoucherOrder`，调用 `createVoucherOrder()` 事务方法落库。落库成功后执行 `XACK` 确认消息。

### Q：Redis Stream 在这里起什么作用？

A：Redis Stream 在这里承担轻量消息队列的作用，把“秒杀资格判断”和“数据库落库”解耦。前台请求只要 Lua 判断通过、消息写入 Stream，就可以返回订单 ID；数据库扣库存和插入订单由后台消费者慢慢处理。

这样可以削峰，避免秒杀流量直接冲击 MySQL。相比普通 List，Stream 有消费者组、消息 ID、Pending List 和 ACK 机制，适合这种需要可靠消费的场景。

### Q：MySQL 最终兜底是怎么做的？

A：有两层兜底。第一层是库存扣减时带条件 `stock > 0`，避免数据库层面扣成负数。第二层是订单表唯一索引 `uk_user_voucher(user_id, voucher_id)`，避免重复订单。

也就是说，Redis 解决高并发入口的快速判断，MySQL 保证最终数据一致性。即使某条重复消息进入消费者，数据库唯一索引和业务查询也会兜住。

### Q：唯一索引的 key 由哪些字段组成？

A：秒杀订单唯一索引由 `user_id` 和 `voucher_id` 组成。因为业务语义是同一个用户对同一个优惠券只能下一单，但不同用户可以买同一张券，同一用户也可以购买不同券。

### Q：用户重复点击或并发下单时，如何保证只生成一单且不超卖？

A：先在 Redis Lua 层解决大部分并发问题。100 人同时抢 10 张券时，Lua 对同一个 Redis key 的执行是串行原子的，每个成功请求都会先检查 `stock > 0`，然后 `HINCRBY stock -1`。当库存扣到 0 后，后续请求直接返回库存不足。

同一个用户重复点击时，Lua 会通过 `HSETNX user:{userId}` 保证只有第一次能设置成功。后续重复请求返回禁止重复下单。

落库时再用 Redisson 的 `lock:order:{userId}` 做用户维度锁，数据库里还有 `uk_user_voucher` 唯一索引。所以从 Redis、分布式锁、数据库三个层面防重复，从 Redis 和数据库两个层面防超卖。

### Q：库存是先写入 Redis 还是数据库？

A：真实库存主数据在 MySQL 的 `tb_seckill_voucher` 表中。服务启动时会把秒杀券库存预热到 Redis 的 `seckill:{voucherId}` Hash 里。秒杀请求先扣 Redis 库存，异步消费者再扣 MySQL 库存并创建订单。

所以运行时是 Redis 先承接请求和预扣库存，MySQL 做最终落库。这样做的代价是短时间内 Redis 和 MySQL 会有异步差，但可以换来高并发入口性能。

### Q：下单后库存扣减和异步落库失败怎么处理？

A：前台下单成功代表 Redis 校验通过并写入 Stream，不代表 MySQL 已经落库。后台消费者落库时会再次扣 MySQL 库存，如果扣减失败会记录日志并返回，不插入订单。

如果消费者处理过程中抛异常，消息不会 ACK，会留在 Stream 的 Pending List。消费者主循环捕获异常后会调用 `handlePendingList()`，从 `ReadOffset.from("0")` 读取 Pending 消息重新处理。

当前项目还没有做库存补偿和订单状态流转，所以生产级设计里我会补充失败订单状态、补偿任务和告警。

### Q：Redis Stream 消费失败后怎么重试？

A：消费者正常消费后会 `XACK`。如果处理失败，没有 ACK 的消息会进入消费者组的 Pending List。代码里主消费循环发生异常后，会调用 `handlePendingList()`，从 Pending List 读取历史未确认消息，重新调用 `handleVoucherOrder()` 处理，成功后再 ACK。

为了避免异常导致线程直接退出，消费循环外层有 `while (running)`，并且失败时会记录日志。Pending List 恢复失败时会短暂 `sleep(20ms)` 再继续。

### Q：Pending List 或死信队列怎么处理？

A：当前项目实现了 Pending List 恢复，但没有单独的死信队列。Pending List 里的消息会被消费者反复读取和重试，成功后 ACK。

如果要生产化，我会补一个重试次数字段或独立失败记录，超过阈值后写入死信队列或失败表，并加告警。这样可以避免同一条坏消息一直卡住恢复循环。

### Q：怎么保证读写一致性？

A：不同场景采用不同策略。秒杀库存是 Redis 先扣、MySQL 异步扣，追求的是高并发场景下的最终一致性；商铺详情缓存是更新数据库成功后删除缓存，下一次查询再重建；热点商铺使用逻辑过期，过期时先返回旧值，再异步重建，优先保证可用性。

所以我不会说所有场景都是强一致。秒杀场景是最终一致，商铺更新场景通过“先更新数据库，再删缓存”减少不一致窗口，热点缓存通过逻辑过期牺牲短时间新鲜度来换稳定性。

### Q：是否有加锁或其他并发控制？

A：有。秒杀入口主要依靠 Redis Lua 原子性；异步落库时用 Redisson 的 `lock:order:{userId}` 做用户维度分布式锁；商铺逻辑过期重建用 `lock:shop:{id}` 互斥锁避免多个线程同时回源；商铺类型缓存重建也用 `lock:shop-type`。

数据库侧也用唯一索引做并发兜底，这是比单纯业务锁更可靠的最终防线。

### Q：缓存和数据库的数据同步/缓存更新策略是什么？

A：商铺详情查询走 `CacheClient.queryWithLogicalExpire()`。缓存里存的是 `RedisData`，包括真实数据和逻辑过期时间。未过期直接返回；过期时如果拿到锁，就提交异步重建任务，当前请求先返回旧数据；拿不到锁也返回旧数据。

更新商铺时，先更新数据库，再删除 `cache:shop:{id}`。下一次查询时如果缓存缺失，会通过互斥锁和双重检查回源数据库重建缓存。

商铺类型是普通缓存，查不到时加锁回源数据库，写入 `cache:type`，新增、修改、删除类型时清理缓存。

### Q：Redis 是怎样查找 MySQL 数据的？

A：Redis 本身不会主动查 MySQL，是应用代码在缓存未命中时回源数据库。比如商铺详情查询时，代码先查 `cache:shop:{id}`；如果没有，再调用 `this::getById` 查 MySQL，查到后写回 Redis。

所以流程是应用层 cache-aside 模式：先读 Redis，未命中读 MySQL，再写 Redis。

### Q：如果 Redis 查不到或发生缓存穿透怎么办？

A：`CacheClient.queryWithPassThrough()` 用空值缓存防穿透。如果数据库也查不到，就把空字符串写入 Redis，并设置较短 TTL，当前项目空值 TTL 是 2 分钟。下次相同不存在 ID 再来，命中空字符串就直接返回 null，不再打数据库。

热点商铺逻辑过期场景下，如果冷启动缓存缺失，会用互斥锁、双重检查和有限重试保护数据库，避免大量请求同时回源。

### Q：是否用了空值缓存、随机过期时间或缓存更新？

A：用了。空值缓存用于防缓存穿透；逻辑过期缓存里会在基础过期时间上增加 60 到 600 秒的随机抖动，缓解大量 key 同时过期造成的雪崩；商铺更新时采用更新数据库后删除缓存的方式。

### Q：项目里用 RedisTemplate 或相关模板做了哪些 Redis 读写操作？

A：项目主要用 `StringRedisTemplate`。登录验证码用 String 存储；登录 token 用户信息用 Hash；秒杀库存和用户下单状态用 Hash；秒杀订单队列用 Stream；关注关系用 Set；点赞和 Feed 流用 ZSet；签到用 Bitmap；附近商铺用 GEO；RAG 会话和回答缓存用 String。

### Q：数据存储上用缓存还是 Redis？

A：如果问的是业务主数据，还是 MySQL 存储，Redis 主要做缓存、临时状态、高并发入口和消息队列。比如商铺、订单、用户、博客这些最终都在 MySQL；Redis 负责提升读性能、承接秒杀流量、做 Feed/点赞/关注共同交集等高频场景。

## MySQL / 数据库设计

### Q：这个电商项目有哪些核心数据表？

A：核心表包括用户表 `tb_user`、用户详情表 `tb_user_info`、商铺表 `tb_shop`、商铺类型表 `tb_shop_type`、优惠券表 `tb_voucher`、秒杀券库存表 `tb_seckill_voucher`、订单表 `tb_voucher_order`、探店笔记表 `tb_blog`、关注关系表 `tb_follow`、签到表 `tb_sign`、评论表 `tb_blog_comments`。

RAG 模块还有知识库相关表：`tb_kb_document`、`tb_kb_chunk`、`tb_kb_ingest_job`。

### Q：用户表、优惠券表、商铺表、订单表等怎么设计？

A：用户表 `tb_user` 存手机号、密码、昵称、头像，手机号有唯一索引。商铺表 `tb_shop` 存名称、类型、图片、区域、地址、经纬度、均价、销量、评分、营业时间等。优惠券主表 `tb_voucher` 存店铺 ID、标题、副标题、规则、支付金额、抵扣金额、类型、状态；秒杀券扩展表 `tb_seckill_voucher` 存 `voucher_id`、库存、开始时间、结束时间。

订单表 `tb_voucher_order` 存订单 ID、用户 ID、券 ID、支付方式、状态、创建和更新时间，并通过 `uk_user_voucher(user_id, voucher_id)` 保证一人一单。

### Q：MySQL 背后的存储引擎是什么？

A：项目建表里大部分表都用 InnoDB。InnoDB 支持事务、行级锁、崩溃恢复和外键能力，适合订单、用户、关注关系这类需要一致性的业务表。秒杀落库时依赖事务和条件更新，InnoDB 更合适。

### Q：知道对象存储是怎么实现的？比如视频、文件、图片等。

A：当前项目没有接云厂商对象存储，图片上传是通过 `UploadController` 接收 `MultipartFile`，生成 UUID 文件名后落到本地目录，默认是 `data/hmdp/imgs`，也可以通过 `APP_UPLOAD_DIR` 环境变量配置。然后 MVC 把 `/blogs/**` 映射到这个本地目录，实现图片访问。

如果生产环境要做对象存储，我会把上传文件写到 OSS/COS/S3 这类服务，数据库只保存 URL、文件名、大小、类型、hash 等元数据。这样可以避免应用服务器磁盘成为瓶颈，也方便 CDN 加速和扩容。

## HTTP / 网络 / 后端基础

### Q：讲一讲 HTTP 协议。

A：HTTP 是应用层协议，常用于浏览器或前端和后端服务通信。它基于请求-响应模型，请求包括方法、URL、请求头、请求体，响应包括状态码、响应头、响应体。我的项目里前端通过 Axios 调后端 REST 接口，后端用 Spring MVC Controller 接收请求并返回统一的 `Result` JSON。

### Q：HTTP 接口是怎么做的？

A：后端用 Spring MVC 写 Controller，通过 `@RestController`、`@RequestMapping`、`@GetMapping`、`@PostMapping`、`@PutMapping` 暴露接口。比如秒杀是 `POST /voucher-order/seckill/{id}`，关注是 `PUT /follow/{id}/{isFollow}`，查询关注 Feed 是 `GET /blog/of/follow`。

接口返回统一封装成 `Result`，成功时 `Result.ok(data)`，失败时 `Result.fail(message)`。

### Q：请求格式是不是 RESTful 风格？

A：整体是偏 RESTful 的风格。资源路径用名词表达，比如 `/blog/{id}`、`/shop/{id}`、`/follow/common/{id}`，通过 HTTP 方法表达动作，比如 GET 查询、POST 新增或提交、PUT 更新状态。

但项目里也有一些业务动作型接口，比如 `/voucher-order/seckill/{id}`、`/voucher-order/claim/{id}`，严格来说不是纯 RESTful，而是为了业务语义更清楚。

### Q：GET、POST 这类请求方式怎么理解？

A：GET 一般用于查询，不应该产生副作用，比如查询商铺、查询博客详情、查询关注状态。POST 一般用于提交或创建，会产生业务变化，比如登录、发布博客、秒杀下单。PUT 常用于更新状态，比如点赞、关注/取关。

在我的项目里，秒杀用 POST，因为它会创建订单；关注用 PUT，因为它改变关注状态；查询热门笔记用 GET。

### Q：请求参数怎么传？

A：项目里主要有三种：路径参数、查询参数和请求体。路径参数用 `@PathVariable`，比如 `/voucher-order/seckill/{id}` 的券 ID；查询参数用 `@RequestParam`，比如分页 current、经纬度 x/y；复杂对象用 `@RequestBody`，比如发布 Blog 或 RAG chat 请求。

登录 token 放在请求头 `Authorization`，支持直接 token，也支持 `Bearer token`。

### Q：Cookie 和 Session 有什么区别？

A：Cookie 存在客户端浏览器，每次请求可以自动携带；Session 通常是服务端保存会话数据，客户端只保存 sessionId。Cookie 更像客户端状态载体，Session 更像服务端会话状态。

我的项目没有使用传统 Cookie Session 登录，而是手机号验证码登录后生成 token，把用户 DTO 存到 Redis Hash：`login:token:{token}`。前端后续通过 `Authorization` 请求头传 token。拦截器从 Redis 读用户并刷新 TTL。

### Q：什么场景用 Cookie，什么场景用 Session？

A：如果是传统 Web 应用、浏览器访问为主，可以用 Cookie 存 sessionId，服务端用 Session 保存登录态。前后端分离或移动端场景更常用 token，因为请求头携带更灵活，也方便跨端。

我的项目是前后端分离，所以选择 `Authorization` token + Redis 存登录态。

### Q：HTTP 状态码怎么分类？

A：1xx 是信息类，实际业务里较少直接处理；2xx 表示成功，比如 200；3xx 表示重定向；4xx 表示客户端错误，比如 400 参数错误、401 未登录、404 资源不存在；5xx 表示服务端错误。

我的项目里登录拦截失败会直接返回 401；业务失败通常还是返回 200 的 JSON，但 `Result` 里会带失败信息。

### Q：2xx、3xx、4xx、5xx 分别表示什么？

A：2xx 是请求成功，3xx 是重定向，4xx 是客户端请求问题，5xx 是服务端处理异常。面试里我会举例：200 成功，301/302 重定向，401 未认证，403 无权限，404 找不到资源，500 服务端异常。

### Q：用户态和内核态有什么区别？

A：用户态是应用程序普通代码运行的状态，不能直接操作硬件和内核资源；内核态是操作系统内核运行的状态，可以操作文件、网络、内存管理等底层资源。两者隔离是为了安全和稳定。

### Q：你写的 Java 代码什么时候处于用户态，什么时候进入内核态？

A：普通 Java 业务逻辑，比如参数校验、对象转换、调用 Service，大部分运行在用户态。涉及系统调用时会进入内核态，比如网络 IO、磁盘文件上传保存、Socket 读写、线程调度、数据库连接底层网络通信等。

例如项目里上传图片 `image.transferTo(new File(...))` 最终会触发文件写入系统调用；访问 Redis/MySQL 的底层网络 IO 也会通过操作系统进入内核态。

### Q：讲一讲 TCP。

A：TCP 是传输层协议，特点是面向连接、可靠传输、字节流、有序、拥塞控制和流量控制。HTTP/1.1 和 HTTP/2 通常跑在 TCP 之上。连接建立通过三次握手，断开通过四次挥手。

项目里前端请求后端、后端访问 MySQL/Redis，本质上底层都依赖 TCP 连接，只是我们在代码里通过 HTTP 客户端、JDBC、Redis 客户端使用它。

### Q：TCP 用什么机制保证可靠连接？

A：TCP 主要通过序列号、确认应答 ACK、超时重传、滑动窗口、流量控制、拥塞控制来保证可靠传输。序列号保证顺序，ACK 确认收到，丢包后重传，窗口控制发送速度。

### Q：TCP 和 UDP 有什么区别？

A：TCP 面向连接，可靠、有序，但开销更大；UDP 无连接，不保证可靠和顺序，但延迟低、开销小。HTTP/1.1 和 HTTP/2 基于 TCP；HTTP/3 基于 QUIC，QUIC 是基于 UDP 实现的可靠传输协议，解决 TCP 队头阻塞等问题。

## Java / Redis 数据结构

### Q：数组和链表有什么区别？

A：数组在内存上通常是连续空间，支持按下标 O(1) 随机访问，但中间插入删除需要移动元素；链表节点不要求连续，插入删除只要改指针，适合频繁插入删除，但按位置查找需要从头遍历，时间复杂度 O(n)。

### Q：Java 线程同步怎么做？

A：常见方式有 `synchronized`、`ReentrantLock`、`volatile`、CAS 原子类、线程安全集合等。`synchronized` 和 Lock 解决互斥，`volatile` 保证可见性和禁止指令重排但不保证复合操作原子性，CAS 适合轻量无锁并发更新。

项目里业务层更多使用分布式并发控制，比如 Redisson 分布式锁、Redis Lua 原子脚本、数据库唯一索引，而不是只靠 JVM 内锁。因为秒杀服务可能部署多实例，`synchronized` 只能锁单 JVM，不能解决分布式场景。

### Q：讲一讲 Redis 数据结构 ZSET。

A：ZSET 是有序集合，每个 member 对应一个 score，可以按 score 排序。它既能保证 member 唯一，又能按分数范围查询。

项目里点赞列表和 Feed 流都用了 ZSET。博客点赞用 `blog:liked:{blogId}`，member 是用户 ID，score 是点赞时间；查询 Top 点赞用户时按 score 取。关注 Feed 用 `feed:{userId}`，member 是 blogId，score 是发布时间，支持滚动分页。

### Q：ZSET 底层的实现原理是什么？

A：Redis ZSET 常见底层是 hash table + skiplist。hash table 用来快速判断 member 是否存在并取 score，skiplist 用来按 score 有序范围查询。小数据量时 Redis 也可能使用压缩结构优化内存。

## AI 求职平台 / 简历解析

### Q：你这个 AI 求职平台从需求到实现是怎么拆分的？

A：这部分是我另一个 AI 求职平台项目，不在当前 HMDP 仓库里。我的拆分思路是先做最小闭环：用户上传简历，系统解析成结构化 JSON；用户输入或粘贴岗位 JD；系统做岗位匹配评分并给出建议；最后再扩展模拟面试。

也就是先把“简历解析 -> 岗位匹配 -> 反馈建议”跑通，再考虑用户体系、历史记录、可视化报告、模拟面试、多轮追问这些增强功能。

### Q：第一阶段先做什么？

A：第一阶段先做简历解析。因为后面的岗位匹配和模拟面试都依赖简历结构化结果。只有把 PDF/DOCX/文本简历解析成标准字段，比如教育经历、项目经历、技能栈、实习经历、获奖经历，后面才能稳定做匹配和提问。

### Q：技术选型怎么做？

A：技术选型优先围绕快速验证和 AI 生态。简历解析、Prompt 调试、文件解析和模型调用，Python 生态成熟，适合快速做原型；如果要接入到我当前 Java 后端体系，也可以把 AI 能力封装成独立服务，通过 HTTP API 给主系统调用。

### Q：为什么选择 Python？

A：因为 Python 在 AI 应用开发里生态更完整，文件解析、向量检索、模型调用、Prompt 编排、数据处理都比较方便。比如处理简历文件、调用大模型、做结构化抽取和评分，用 Python 可以更快迭代。

但如果是当前 HMDP 的 RAG 模块，我用的是 Java + LangChain4j + Ollama + Milvus，因为它和 Spring Boot 主项目集成更直接。

### Q：哪些功能先做，哪些功能先不做？

A：先做用户价值最直接、实现链路最短的功能：简历上传、简历结构化解析、岗位 JD 输入、匹配评分、修改建议。先不做复杂的社交、完整招聘平台、支付、企业端、复杂权限和大规模推荐。

原因是 AI 项目早期风险在于“解析和匹配结果是否有用”，不是页面功能多不多。所以先验证核心效果。

### Q：接入大模型时怎么选型？

A：我会从效果、成本、速度、部署方式四个维度选。简历解析要求结构化输出稳定，优先选指令跟随能力强、JSON 输出稳定的模型；模拟面试要求对话能力；如果涉及隐私，可以考虑本地模型或私有化部署。

当前 HMDP 的 RAG 模块用 Ollama 接本地模型，默认配置是 `qwen2.5:7b` 做聊天，`qwen3-embedding:0.6b` 做向量 embedding。

### Q：用国内模型还是国外模型？

A：如果项目面向中文简历和中文岗位，国内或中文能力强的模型会更合适，成本和访问稳定性也更好。国外模型通常通用能力强，但成本、网络和数据合规要考虑。

我的策略是开发阶段可以多模型对比，生产阶段根据成本、稳定性和隐私要求选择。如果简历数据敏感，本地 Ollama 或私有化模型更安全。

### Q：为什么选择这些模型？

A：选择标准不是只看模型排名，而是看任务适配度。简历解析要结构化能力，岗位匹配要理解 JD 和候选人经历，模拟面试要追问能力。HMDP 的 RAG 用 Qwen + Ollama，是因为本地部署简单，中文效果够用，和 Java 的 LangChain4j 集成成本低。

### Q：使用 AI 编程工具时，你是怎么给模型下指令的？

A：我一般会明确角色、任务、输入输出格式和约束。比如让模型扮演后端工程师，任务是实现某个接口，输入是 DTO 和业务规则，输出要求包括代码、边界条件和测试点。对于简历解析，我会要求输出固定 JSON schema，缺失字段用空数组或 null，不允许自由发挥。

### Q：是否会指定角色、任务和输出格式？

A：会。尤其是结构化任务必须指定输出格式。比如简历解析要求输出 `basicInfo`、`education`、`skills`、`projects`、`internships` 等字段；岗位匹配要求输出总分、技能匹配、项目匹配、短板建议和修改建议。这样后端才能稳定解析模型结果。

### Q：简历解析具体怎么做？

A：流程是先读取简历文件内容，把 PDF/DOCX/TXT 转成纯文本，然后做清洗，比如去掉多余空格和页眉页脚；再把文本交给大模型，要求它按固定 JSON schema 抽取字段；最后后端做 JSON 校验和字段兜底。

如果要增强准确率，可以按模块拆分 Prompt，比如基础信息、教育经历、项目经历、技能栈分别抽取，最后合并。

### Q：大模型输出的结构化 JSON 包含哪些字段？

A：可以包含基础信息、教育经历、技能列表、项目经历、实习经历、工作经历、获奖证书、自我评价等。项目经历里至少包括项目名称、技术栈、职责、亮点、难点、结果；技能可以按语言、框架、中间件、数据库、AI 工具分类。

### Q：岗位匹配或岗位评分怎么实现？

A：先把岗位 JD 也结构化，提取岗位名称、必须技能、加分技能、经验要求、项目要求、学历要求。然后把简历结构化结果和 JD 做匹配，可以按技能匹配、项目相关度、经验年限、关键词覆盖、亮点强度等维度打分。

模型可以负责语义判断和建议生成，但评分规则最好有一部分固定权重，避免每次输出漂移。

### Q：岗位描述从哪里来？

A：可以由用户从招聘网站复制岗位 JD，也可以后续接招聘平台 API 或爬虫采集。早期我会让用户手动粘贴 JD，因为实现简单，也能覆盖真实求职场景。

### Q：如何把岗位描述和简历做匹配？

A：先把双方都结构化。岗位侧拆成技能、职责、要求；简历侧拆成技能和项目经历。然后做关键词匹配和语义匹配，最后让模型基于证据给出评分、匹配理由和改进建议。输出时要告诉用户哪些经历支撑了匹配，哪些要求没有覆盖。

### Q：AI 帮你实现代码后，你怎么验收？

A：我会先本地运行，检查接口是否能启动、核心流程是否能跑通，再用样例数据测试边界条件。比如简历解析要测试不同格式文件、缺字段简历、很长项目经历；岗位匹配要测试强匹配、弱匹配、无关岗位。

对于当前 HMDP 项目，我也会看代码是否符合已有分层，是否绕过 Redis/Lua/Stream 这些关键路径。

### Q：不满意时怎么修改提示词或迭代功能？

A：我会先定位问题是输入不清楚、输出格式不稳定，还是模型理解错。如果是格式问题，就收紧 JSON schema 和示例；如果是理解错，就补充反例和判断规则；如果是功能问题，就拆小任务，不让模型一次做太多。

### Q：模拟面试功能有没有做过？

A：设计上可以做。流程是用户选择岗位和简历，系统根据岗位要求和简历项目生成问题；每次用户回答后，模型根据回答质量追问，并给出评分和改进建议。问题来源可以结合 JD、简历项目、技术栈和常见面试题库。

### Q：运动、步数、排行榜这类功能有没有做过？

A：当前 HMDP 项目没有完整微信运动模块，但有签到、关注关系、Feed 和排行榜类似能力。比如签到用 Redis Bitmap 记录，点赞排行用 ZSet，Feed 流用 ZSet。如果设计步数排行榜，可以复用 ZSet，member 是用户 ID，score 是步数。

### Q：这些功能的数据怎么记录？

A：步数这种高频变化数据可以当天写 Redis ZSet，比如 `steps:{yyyyMMdd}`，score 是步数，member 是用户 ID，查询排行榜用 `ZREVRANGE`。如果要持久化，可以定时落 MySQL。关注关系仍然存在 MySQL 和 Redis Set，查询好友步数时先取关注列表，再取这些用户的步数。

## 接口设计 / 用户关系 / 关注功能

### Q：用户关注和粉丝关系怎么存储？

A：当前项目用 `tb_follow` 表存关注关系，字段是 `user_id` 和 `follow_user_id`。`user_id` 表示发起关注的人，`follow_user_id` 表示被关注的人。同时 Redis 用 Set 缓存某个用户关注的人，key 是 `follows:{userId}`，value 是被关注用户 ID。

### Q：表结构怎么设计？

A：关注表至少需要主键 ID、`user_id`、`follow_user_id`、创建时间，并对 `(user_id, follow_user_id)` 建唯一索引，防止重复关注。当前项目就是这个思路。

### Q：用户表里是否应该用字段存关注者 ID？

A：不应该。关注关系是多对多关系，如果把关注者 ID 存在用户表的一个字段里，会导致字段无限膨胀、难以查询、难以维护索引，也不符合范式。应该单独建关注关系表。

### Q：这个表应该有几个字段？

A：最基础字段是 `id`、`user_id`、`follow_user_id`、`create_time`。如果要扩展，还可以加状态、来源、分组、备注等，但核心查询只需要用户 ID 和被关注用户 ID。

### Q：关注功能接口怎么设计？

A：当前项目有三个接口：`PUT /follow/{id}/{isFollow}` 用于关注或取消关注；`GET /follow/or/not/{id}` 判断是否关注；`GET /follow/common/{id}` 查询共同关注。关注时先写 MySQL，再写 Redis Set；取消关注时删除 MySQL，再从 Redis Set 删除。

### Q：共同好友功能接口怎么设计？

A：可以设计成 `GET /follow/common/{targetUserId}`。实现时拿当前登录用户 ID 和目标用户 ID，分别拼出 `follows:{currentUserId}` 和 `follows:{targetUserId}`，用 Redis Set 的 `intersect` 求交集，再按 ID 查用户信息返回。

当前项目的 `followCommons()` 就是这样实现的。

### Q：设计一个类似微信运动的平台需要哪些接口？

A：至少需要上传步数接口、查询今日步数接口、查询好友排行榜接口、查询历史步数接口、点赞/鼓励接口、权限控制接口。结合当前项目，可以用登录系统识别用户，用关注关系确定好友范围，用 Redis ZSet 做当天排行榜，用 MySQL 持久化历史记录。

### Q：如何查询“我关注的人”和“关注我的人”？

A：“我关注的人”查 `tb_follow where user_id = 当前用户`；“关注我的人”查 `tb_follow where follow_user_id = 当前用户`。如果走 Redis，`follows:{userId}` 可以快速得到我关注的人；粉丝列表如果高频，也可以维护反向 Set，比如 `followers:{userId}`。

当前项目只缓存了正向关注 Set，粉丝推送时是通过 MySQL 查询关注我的人。

### Q：互相关注或共同关注的判断条件是什么？

A：互相关注是 A 关注 B，且 B 也关注 A，也就是存在两条关系：`(A, B)` 和 `(B, A)`。共同关注是 A 和 B 关注了同一个 C，可以用两个用户的关注 Set 求交集。

### Q：步数/运动数据与关注关系结合时，应该返回哪些数据？

A：排行榜可以返回用户 ID、昵称、头像、今日步数、排名、是否已点赞。数据来源是关注关系决定可见用户范围，步数来自 Redis ZSet 或 MySQL 统计，用户基础信息来自用户表。
